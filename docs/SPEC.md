# SPEC: Next Notes – Poznote als Nextcloud-App

Stand: M0, 2026-11-02. App „Next Notes“, App-ID `nextnotes`, Namespace `OCA\NextNotes`, Tabellenpräfix `nextnotes_` (ADR 0001). Nextcloud 35 (35.0.x), PHP 8.3–8.5 (§1.3). Upstream: Poznote `6.136.2` / `7e2e0b6a` (`UPSTREAM.md`).
Grundlagen: `docs/INVENTORY.md` (Inventur A/B), `docs/adr/0002`–`0017`.

**Leitprinzipien** (entschieden, Thomas 2026-11-02)
1. Upstream-Nähe im Frontend, wo sie billig ist: Upstream-Updates sollen per `git merge` übernehmbar bleiben. Dateien in `src/` werden nur gezielt direkt geändert; jede Änderung steht in §11.1. Keine Build-Zeit-Patches (ADR 0007, 0013).
2. Das Original ist Vorlage, kein Zwang. Wo eine schlankere, wartbarere oder besser in Nextcloud integrierte Lösung möglich ist, wird sie gewählt – auch im Frontend. Einheitlichkeit vor 1:1-Treue.
3. Backend komplett neu nach Nextcloud-Konvention: Controller → Service → Mapper, Rechteprüfung zentral (§3). Kein Upstream-Backend-Code zur Laufzeit, keine Mischformen. `api/v1`-Pfade und JSON-Formate bleiben gleich, soweit das Frontend sie braucht.
4. Bugs im Original werden nicht übernommen, sondern gefixt (§11.2). Frontend-Bugfixes sind direkte Änderungen in `src/` (§11.1) und Kandidaten für Upstream-PRs.
5. Nur Hell/Dunkel nach NC-Theme; Zusatz-Themes, CSS-/Font-Upload, eigene Schriften gestrichen (ADR 0016).
6. Technische Entscheidungen (Struktur, Schnittstellen, Bibliotheken) treffen Architekt/Lead nach „schlank, wartbar, Nextcloud-nativ“. `[THOMAS]` nur für Produkt-, Datenmodell-mit-Nutzerwirkung- und Datenschutzfragen.

### 1.2 Build (`make -C nextnotes build`, reproduzierbar)
1. Kopiert `src/public/js/**` (ohne gestrichene Dateien laut `bundles.json`: `offline-*`, `pwa/*`, `sw.js`, `two-factor.js`, `login-page.js`, `ai-*.js`, `speech-to-text.js`, `backup-*.js`, `restore-import.js`, `git-*.js` …) in den Build (Upstream-Änderungen sind bereits direkt in `src/`, §11.1).
2. Konkateniert nach den Gruppen aus `src/public/index_js.php` (`head`, `app`) in `nextnotes/js/nextnotes-head.js`, `nextnotes/js/nextnotes-app.js` (klassische Skripte, Endung `.js`, nie `.mjs` – ADR 0006). Eigene Seiten (M3c1: `revisions`, `attachments`) als Bündel `nextnotes-page-<seite>.js/.css` aus `bundles.json` `pages` (CSS = `cssPages`, Skripte in der Reihenfolge der Upstream-Seite; `check-upstream` vergleicht sie mit `src/public/<seite>.php`).
3. CSS analog (`index_css.php`, `css_assets.php`, `dark_mode_css.php`) → `nextnotes/css/*.css`; `nextnotes-tokens.css` danach. `css/index-mobile.css` → `nextnotes-mobile.css` in `@media (max-width: 800px)` (ersetzt das `media`-Attribut, das `addStyle` nicht kennt). `@font-face`-Regeln mit `webfonts/` (Inter) entfallen im Build, `Inter` in `font-family`/`font`-Werten wird zu `var(--font-face)` (ADR 0016 Nachtrag; `bundles.json`). Spezifität: jede Upstream-Regel +1 ID-Stelle gegen NC-Kern-CSS, Zusatz vor Pseudo-Element samt folgenden Pseudo-Klassen, Formular-Reset in `nextnotes-layout.css` (ADR 0017; `build/css-bump.mjs`). Der Build bricht ab, wenn ein Zusatz hinter einem Pseudo-Element steht oder sich die Regelzahl ändert; `check-upstream` (e2) parst Quellen und Bundles mit Chromium (Regeln vor/nach Zusatz gleich, keine Regel nur durch den Zusatz ungültig). Bis M4 ausgeschlossen: `calendar.js`, `background-settings.js` (rufen beim Laden die M4-Routen `api/v1/calendar/*.php` bzw. `api_upload_background.php`); `calendar.js` seit M4f, `background-settings.js` seit M4g wieder im App-Bündel.
4. Vendor (`codemirror-dist`, `excalidraw-dist` + Assets, `mermaid`, `katex`, `highlight`, `Sortable`) unverändert nach `nextnotes/js/vendor/`, Stylesheets (`katex.min.css` + Fonts, `url()` umgeschrieben) nach `nextnotes/css/vendor/` – `Util::addScript`/`addStyle` laden nur aus `js/`/`css/` (M3-plan r2); Excalidraw-Assetpfad per InitialState. Einzige Build-Abhängigkeit: `esbuild` (gepinnt, Lockfile, Minify nur Whitespace/Syntax).
5. `src/i18n/*.json` → `nextnotes/i18n/` (für `/system/i18n`; dazu `i18n/default-note-titles.json` = „Neue Notiz“ aller Sprachen für die Titelübersetzung der Hauptansicht) und `nextnotes/js/i18n/nextnotes-i18n-<lang>.js` (mit `en` als Rückfall eingemischt, §1.4). Keine Upstream-PHP-Dateien im Paket. Konvertierung (M4b): Port der Upstream-Parser als `lib/Service/Convert/{MarkdownRenderer,HtmlToMarkdown,EmbeddedDiagrams,MediaTags}` (Rohfassung per `build/port-convert.php`: Funktionen → statische Methoden, `preg_*` → `Pcre` über Trait `PcreCalls`, `t()` → Übersetzer der App; B46 danach von Hand), keine Composer-Abhängigkeit. Parität über Fixture-Korpus (`tests/nextnotes/fixtures/convert`, Erwartung per Host-PHP aus den Upstream-Funktionen). `build/upstream-ported.txt` hält sha256 der Upstream-Basis je nachgebauter Datei; `check-upstream` (f) wird rot, wenn sich eine ändert („Port prüfen“), (g) verbietet direktes `preg_*` in `Service/Convert`, Import und Export.
6. Keine Netzwerkzugriffe, keine Zeitstempel in Ausgaben; gleiche Eingabe → gleiche Prüfsummen.
`make -C nextnotes dist` (M7a, `build/dist.sh`): baut aus einem sauberen `git worktree` von `HEAD` (Arbeitsbaum ändert das Paket nicht); `build/node_modules` per Symlink aus dem Hauptbaum, nur bei Byte-gleicher `build/package-lock.json` (sonst Abbruch, kein Netz, kein `npm install`); gibt tar-, gzip-, esbuild- und node-Version aus. Version aus `appinfo/info.xml`, `SOURCE_DATE_EPOCH` = Commit-Zeit; tar normalisiert (`--format=gnu --sort=name --mtime=@<Commit-Zeit> --owner=0 --group=0 --numeric-owner --mode=u=rwX,go=rX`, `LC_ALL=C`) + `gzip -n -9`, eine Wurzel `nextnotes/`. Ausschlüsse nur in `build/dist-exclude.txt` (gleiche Liste für `dev/nextcloud/install-app.sh`): `.gitignore`, `Makefile`, `build/`, `css-src/`, `dist/`, `js-src/`, `screenshots/`. Ausgabe `nextnotes/dist/nextnotes-<version>.tar.gz` + `.sha256` (git-ignoriert), danach `dev/nextcloud/check-dist.sh`. Reproduzierbar für dieselbe Werkzeugkette.

### 1.4 Laufzeit
- PageController liefert je Ansicht eine `TemplateResponse` (ADR 0004), lädt Bundles per `OCP\Util::addScript('nextnotes', …)` / `addStyle`, Daten per `IInitialState::provideInitialState`.
- Reihenfolge der Skripte: `i18n/nextnotes-i18n-<lang>.js` → `nextnotes-bootstrap.js` → `nextnotes-head.js` → Einzelskripte (CodeMirror, `lazy-libs`, highlight) → `nextnotes-app.js` → `nextnotes-late.js` → Seitenskript (alle `defer`, Reihenfolge bleibt).
- Settings: Benutzer über `OCP\Config\IUserConfig` (@since 32), Admin über `IAppConfig` + `OCP\Settings\ISettings` (Admin-Abschnitt: Embed-Domains, Anhangsgrenzen, Quota).
- Admin-Formular (M4a): `Settings\AdminSettings`/`AdminSection` (NC-Verwaltung → Next Notes), Speichern `POST /admin/settings` (`AdminSettingsController`, ohne `NoAdminRequired`, CSRF aktiv): `allowed_iframe_domains` (≤ 100 exakte Hosts, `EmbedDomainService::normalize`), `attachment_max_file_mb` 1–2048, `attachment_quota_mb` 1–1 048 576; ein Fehler → 400 mit `errors[]`, nichts gespeichert. `EmbedDomainService` ist einzige Quelle für `HtmlSanitizer::iframeSrcIsTrusted`, `CspFactory` und InitialState `allowedIframeDomains`.
- i18n: Upstream-Wörterbücher unverändert; Sprache aus `IL10N::getLanguageCode()` abgebildet (`de_DE`→`de`, `zh_CN`→`zh-cn`, `pt_BR`/`pt_PT`→`pt`, sonst `en`). Wörterbuch als statische, vom Browser gecachte JS-Datei je Sprache (nicht InitialState: ≈ 300 KB je Seite, nicht cachebar); der Adapter beantwortet `/system/i18n` daraus ohne Netz-Request (Route bleibt für Kompatibilität; M3-plan r2, O1).

## 2. Datenmodell

Konventionen: IDs `BIGINT` Autoinkrement; Zeitpunkte `BIGINT` Unix-Sekunden UTC aus `ITimeFactory` (keine DB-Zeitfunktionen); Flags `SMALLINT` 0/1 (Upstream liefert 0/1); UIDs `STRING(64)`; Circle-`singleId` `STRING(64)`; lange Texte `TEXT` (`Types::TEXT`); Strings ≤ 4000. Keine Fremdschlüssel-Constraints (NC-üblich), Kaskaden im Service. NOT-NULL-Spalten nie mit Default `''`. Namen ≤ 63 Zeichen inkl. Präfix (`MigrationService::ensureOracleConstraints`). Index-Namen tabellenweit eindeutig (Präfix `nn_`).

**UID-Regel** (Lead, 2026-11-02): Nextcloud kann eine gelöschte UID neu vergeben. Deshalb bleibt nach einer Kontolöschung keine UID stehen, die Rechte verleiht. Rechtetragende UID-Spalten: `workspaces.owner_id` (bei `owner_type=user`), `workspaces.created_by` (nur für verwaiste/eingefrorene Team-Workspaces, ADR 0003), `ws_shares.share_with`, `assignments.owner_uid`, `submissions.student_uid`; sie werden bei Kontolöschung gelöscht, NULL gesetzt oder übertragen (§8). Reine Anzeige-/Historienspalten (`created_by`, `updated_by`, `feedback_by` in Notizen, Anhängen, Snapshots, Aufgaben, Abgaben) verleihen nie Rechte und werden ebenfalls NULL gesetzt; wo der Name gebraucht wird, steht er in einer `*_name`-Spalte.

Ordner verschieben und `move_notes` prüfen unter der Sperre von Quelle und Ziel erneut und bestätigen nach dem Verschieben, dass bei der Eigene-Notiz-Ausnahme nur Notizen des Akteurs angekommen sind (`AccessService::moveLeaving`, sonst 403 und Rollback). Archiv bei Team-Quelle = „Archives“ desselben Teams (anlegen nur mit verwalten). Systemverwaltetes (Notizen `role≠note`, Inhalte von `kind=assignments`-Workspaces und Ordnern mit `assignment_id`) verlässt nie seinen Workspace und wird nicht kopiert (deny by default bis M6). Bewusste Ausnahme: „In privat umwandeln“ (M5b) übernimmt alle Notizen.

**Lebenszyklus (M5b):** `DestroyingCircleEvent` (aus Circles' `manage()`, in CLI synchron, im Web im Loopback-Request) und `CircleDestroyedEvent` (Loopback) → `TeamLifecycleService::teamDeleted`: nur für Teams mit Team-Workspaces; bedingtes UPDATE `active → orphaned` (`orphaned_at`), nur beim ersten Übergang Benachrichtigung `team_orphaned` an alle `created_by`. `MembershipsRemovedEvent` (direkt, geerbt, Gruppe) → `MembershipsRemovedListener::onLeft(teamId, uid)` (Schnittstelle M6) → `memberLeft`: nur bei bestehendem Team (`exists()` ≠ null) und strikt geprüftem Level 0 (`TeamService::currentLevel`, ohne Cache und Probe-Regel, Fehler → nichts tun); löscht Erinnerungen und Erwähnungs-Status der uid an Notizen der Team-Workspaces (`kind=normal`) dieses Teams und queued ihre Hintergrundbilder dort. Listener fangen jede Ausnahme selbst (Log `error`), Circles-Klassen nur in `TeamService` (Events als Namen registriert). Umwandeln (`TeamLifecycleService::makePrivate`): nur `created_by` bei Zustand `orphaned` (unter Sperre erneut geprüft) **und** eindeutig fehlendem Team (`TeamService::exists()` = null vor der Transaktion; Team vorhanden – z. B. Löschen nach `DestroyingCircleEvent` gescheitert – oder `TeamUnavailableException` → 403 ohne Änderung, Review M5b-r1), Name bei Kollision mit eigenem Workspace „<Name> Team“, „<Name> Team 2“ …; entfernt Freigabezeilen (würden sonst wirken), Erinnerungen, Erwähnungs-Status und Sperren anderer Konten und alle Hintergrundbilder des Workspace (Ordner einzelner Konten sind über `ISimpleFolder` nicht auflistbar; auch der eigene Hintergrund wird zurückgesetzt); keine Quotenprüfung (sonst Datenverlust nach Fristende), die Team-Zeile bleibt.

**Ohne Teams-App:** `TeamService::isAvailable()` false → alle Teams gelten als **eingefroren** (Zeilen oben); private Workspaces unverändert. `TeamService` nutzt OCP, wo es reicht: `ITeamManager::hasTeamSupport()` (@since 34) für die Verfügbarkeit, Existenz/Name über `TeamService::exists()` (Circles, Owner als Initiator; nicht `getTeam()`, siehe §14), Mitgliedschaften über `CirclesManager::probeCircles` mit eigener Probe (Probe-Regel), Mitgliederlisten über `Circle::getInheritedMembers` (lokale Benutzer mit Status Member); `getTeamsForUser()`/`getMembersOfTeam()` werden nicht genutzt (Kern-Standardprobe ohne Probe-Regel). Level über `CirclesManager::getLink`, dazu Events. `TeamService::exists()` liefert „fehlt“ nur, wenn Circles eindeutig „keine Zeile“ meldet; föderierte/fremd verwaltete Kreise und jeder andere Fehler → unbekannt (`TeamUnavailableException`), daraus folgt nie `missing_count`/verwaist (M5c). `TeamService::members()` prüft keine Rechte des Aufrufers: nur nach `read` am Workspace aufrufen (M5d). Ein Circles-Fehler oder „Team nicht gefunden“ beim Zugriff ändert nie den gespeicherten Zustand (nur 404 für diesen Request).

## 4. API

### 4.1 Basis-URL und Routen
- Registrierung in `appinfo/routes.php` (gleiche Reihenfolge wie `src/public/api/v1/index.php`, damit `check-upstream` diffen kann). Keine OCS-Routen (OCS-Hülle würde das JSON-Format ändern).
- Pfade: `/apps/nextnotes/api/v1/<Upstream-Pfad>`; Basis serverseitig per `IURLGenerator::linkToRoute('nextnotes.page.index')` (entspricht `generateUrl('/apps/nextnotes')` aus `@nextcloud/router` im Browser; `generateUrl` ist eine JS-Funktion, `IURLGenerator` hat sie nicht) → InitialState `nextnotes/config` `{ baseUrl, apiBase, uid, displayName, lang, teamsAvailable, excalidrawAssetPath, allowedIframeDomains, hiddenUiElements }`.
- Parameter `{id}`, `{noteId}`, `{taskId}` mit Requirement `\d+` bzw. Upstream-Format; `{tag}` `[^/]+`; `{name}` `.+` (Workspace-Schlüssel kann Anzeigenamen mit `/` enthalten, nur PATCH/DELETE `/workspaces/{name}` ohne Folgesegment; POST `/workspaces/{name}/make-private` – Namen enthalten kein `/`, Langformen enden auf `)`).
- Antworten: `JSONResponse` mit identischem Aufbau und Fehlerformat wie Upstream (`sendError`). ETag bei `GET /notes/{id}` wie Upstream. Vorübergehende DB-Sperren (`OCP\DB\Exception` mit Grund Sperr-Timeout/Deadlock, v. a. SQLite „database is locked“) → 503 mit `Retry-After: 2` im selben Fehlerformat, nie 500 (M2d). Schreibende Transaktionen mit Sperre beginnen mit der Sperranweisung (SQLite-WAL: kein Lesen vor dem ersten Schreiben).

### 4.4 Workspace-Schlüssel
Upstream adressiert Workspaces per Name (`/workspaces/{name}`, `?workspace=`). Schlüssel = Name bei eigenen Workspaces; bei Team- oder geteilten Workspaces `"<Name> (<Team- bzw. Besitzername>)"`, falls der Name in der sichtbaren Menge sonst doppelt wäre. Bleibt der Schlüssel doppelt (gleicher Name und Besitzername): `"<Name> (<Besitzername>, #<id>)"`; diese Langform wird immer akzeptiert. `WorkspaceService::resolveKey(uid, key)` bildet zurück; unbekannt → 404 (M2-plan r2). Seiten (`index.php?workspace=` u. a.): unbekannter Schlüssel → Standard-Workspace des Benutzers statt 404 (kein Leck, nur sichtbare Workspaces werden aufgelöst; M3-plan r2, O3). Rename-Bodies werden ohne Zusatz gespeichert. Bewusste Ausnahme von „kein GET mit Seiteneffekt“ (§4.5): der erste GET (Seite oder API) ohne eigenen Workspace legt über `WorkspaceService::ensureDefault` den Standard-Workspace an (§2, O5); idempotent, danach ohne Wirkung.

### 4.5 CSRF und Attribute
- Alle schreibenden Routen (POST/PUT/PATCH/DELETE): CSRF-Prüfung aktiv (kein `NoCSRFRequired`). NC prüft CSRF bei jeder Methode ohne `NoCSRFRequired` (`SecurityMiddleware::isInvalidCSRFRequired`), daher auch GET-API-Aufrufe über den Adapter mit Token.
- `#[NoCSRFRequired]` nur für: Seiten-GETs (PageController; das Such-Formular `POST index.php` prüft CSRF über das versteckte Feld `requesttoken`), GET-Downloads/Medien (Anhänge, Exporte, Hintergrundbild, Audio-Player). Regel: kein GET mit Seiteneffekt; einzige Ausnahme Erstanlage des Standard-Workspace (§4.4).
- Alle Benutzerrouten `#[NoAdminRequired]`. Admin-Einstellungen nur über `ISettings`-Formular (Admin-geprüft).
- `#[UserRateLimit]` (@since 27) auf Drag&Drop-Notizanlage, Export-ZIP und Upload; Personensuche `GET /users/search` 30/min (M5d).
- Hintergrundbild (M4g, B43): `api_upload_background.php` POST ≤ 5 MiB (413), nur JPG/PNG/GIF/WebP nach Inhalt (`IMimeTypeDetector::detectContent`, sonst 400), 20/min, Schreibrecht auf den Workspace (sonst 403); GET Status/Bild mit Leserecht, nur eigenes Bild (sonst 404), `nosniff`, `inline`, CSP `default-src 'none'; sandbox`. Speicher `IAppData` `backgrounds/<workspaceId>/<uid>/<scope>.<ext>`; Deckkraft je Workspace-ID (`bg_opacity_<id>` 5–25), Upstream-Schlüssel `background_opacity_<name>` wird in der Settings-API darauf abgebildet (Umbenennen behält Bild und Deckkraft). Bereich nur `background` (Speed Dial entfernt, M6z; sonst 400).
- Erwähnungs-Benachrichtigung (M4g): höchstens 20 Empfänger je Speichervorgang (`MentionService::MAX_NOTIFY`), weitere still ignoriert.
- Export Einzelnotiz (M4c): `api_export_note.php` und `api_download_note.php` je 30/min je Benutzer (Export auch Druckansicht); ZIP (Markdown/HTML mit Anhängen) ≤ 1 GiB Summe (`ExportArchive::MAX_EXPORT_BYTES`), im NC-Temp-Ordner gebaut und gestreamt; `html_embedded` bettet höchstens 32 MiB Bilder ein (`MAX_EMBED_BYTES`), sonst 413; Markdown → HTML (HTML-Export/Druck einer Markdown-Notiz) mit der Render-Grenze 384 KiB, Markdown-Export einer Markdown-Notiz ohne Grenze.

Sanitizer; 1 MiB nicht unter 1 s erreichbar, Spannen über ≈ 1 Mio Zeichen treffen die PCRE-Backtrack-Grenze). `/convert-*` 60/min, Drop-Import 20/min je Benutzer. Messung (PHPUnit `DiaryTest`, 1 031 Einträge à 16 KiB in einem Monat): `entries.php` 50 IDs ≤ 2 s, Render-Anteil ≤ 1 s, Seite ≤ 2 s und ≤ 2 MiB.

### 4.6 CSP
Jede `TemplateResponse` erhält ihre Policy aus `Http\CspFactory` (ADR 0006, 0012). Templates enthalten keine ausführbaren Inline-Skripte und keine `on…=`-Handler; Daten über InitialState oder JSON-Inseln (`type="application/json"`).
Druckansicht `api_export_note.php?format=html&disposition=inline` (`templates/export_print.php`, NC-Grundlayout): dieselbe Policy wie `index.php?note=` (`frame-src 'self'` + Embed-Domains, ADR 0012 Nachtrag M4c), Skript `js/nextnotes-print.js` mit JSON-Insel.
`trash.php` (M4e): Vorschau zeigt Notizinhalt mit Einbettungen → dieselbe Policy wie `index.php?note=` (`frame-src 'self'` + Embed-Domains, `CspFactory::NOTE_VIEWS`, ADR 0012); die übrigen Listen-Seiten haben die Grundpolicy.
`excalidraw_editor.php`: Bild einfügen meldet `script-src wasm-eval` (pica prüft WebAssembly); Verkleinerung läuft über den JS-Rückfall, keine Ausnahme (ADR 0012 Nachtrag M4a).
**Ausgaberegel Templates** (M3-plan r2): jede `$_`-Ausgabe mit `p()` bzw. escapender Übersetzungshilfe; JSON-Inseln mit `JSON_HEX_TAG|JSON_HEX_AMP|JSON_HEX_APOS|JSON_HEX_QUOT`; `print_unescaped` nur für mit `HtmlSanitizer` gespeicherten Notizinhalt, JSON nach dieser Regel und feste Bausteine (Allowlist, per Test geprüft); Benutzerdaten nie in `data-action`, `style`, `on…`. Ausnahme `style`: nur serverseitig geprüfte Farbwerte (Workspace-, Ordner-, Notizfarbe als Hex/Farbname bzw. Palettentoken, `IndexViewService`), ausgegeben mit `p()`. In `templates/index.php` genau ein `print_unescaped` (Schleife der JSON-Inseln). Upstream-Inline-Skripte der Hauptansicht → JSON-Inseln `nextnotes-globals` (Whitelist von Globals) und `nextnotes-body` (Body-Klassen/-Attribute, Root-Variablen, `?workspace=` per `replaceState`), vom Adapter angewendet (M3a2).

| Mitglied tritt aus (auch indirekt über Gruppe/verschachteltes Team) | Circles `MembershipsRemovedEvent` (M5b; Level danach strikt erneut geprüft) + Prüfung des effektiven Levels bei jedem Zugriff | sofort: kein Zugriff auf Team-Workspaces; Erinnerungen, Erwähnungs-Status und Hintergrundbilder der uid in den Team-Workspaces des Teams werden gelöscht (M5b, nie Inhalte aus `kind=assignments`); eigene Abgabe nur noch lesbar (kein Bearbeiten/Abgeben, keine Löschfrist); `left_team_at` setzen (M6f: alle Abgaben des Schülers in Aufgaben des Teams, nur bei aktivem Team – Austritts-Events beim Auflösen setzen nichts; der Listener beachtet auch Teams ohne Team-Workspace, aber mit Aufgaben); Abgabe bleibt vollständig für Lehrkräfte (ADR 0008 e). Ist das ausgetretene Mitglied `owner_uid` einer Aufgabe: Übergang nur unter den Bedingungen aus §9.7, sonst bleibt `owner_uid` |
| Rolle herabgestuft (Level < 4) | Circles `CircleMemberEditedEvent` (optional) + tägliche Prüfung im `CleanupJob` | Rechte folgen sofort der aktuellen Rolle (§3); ist das Mitglied `owner_uid`: Übergang nur unter den Bedingungen aus §9.7, sonst bleibt `owner_uid` |
| Teams-App deaktiviert/fehlt | `TeamService::isAvailable()` | „eingefroren“ (§3): Team-Workspaces lesbar für `created_by`, Aufgaben und Abgaben für `owner_uid` (read/export, §9.7), Schüler nur eigene Abgaben; keine Schreibzugriffe, keine Löschfrist, nichts wird gelöscht; nach Reaktivierung automatisch normal |
| Lehrkraft löscht Aufgabe | `DELETE /api/v1/assignments/{id}` (§9.5) | einziger manueller Löschweg für Abgaben: Aufgabe, Vorlage, alle Abgaben, Kopie-Notizen, Anhänge, Snapshots; `markProcessed` für zugehörige Benachrichtigungen |
| App deaktiviert | – | Daten bleiben; Jobs laufen nicht (NC-Standard) |
| App entfernt (`occ app:remove`) | – | Tabellen und `IAppData` bleiben (NC-Standard); `occ nextnotes:purge --force` löscht alles (bewusste Admin-Aktion bei Deinstallation) |
| Gruppe gelöscht | `GroupDeletedEvent` (@since 18) | erst relevant mit Gruppen-Freigaben (ADR 0014 Option 3) |
Zusätzlich (Lead, 2026-11-02): `CleanupJob` prüft täglich jede Zeile in `nextnotes_teams` mit `state=active` über `TeamService::exists()` (nicht `ITeamManager::getTeam()` direkt, §14; unbekannt zählt nie), aber nur, wenn Circles aktiv ist und fehlerfrei antwortet; meldet er zweimal hintereinander „Team fehlt“ (`missing_count`), wird das Team `orphaned` (normale 30-Tage-Frist mit Benachrichtigung). Ein Lauf mit Fehler/deaktiviertem Circles ändert den Zähler nicht; „Team vorhanden“ setzt ihn auf 0. Manuell: `occ nextnotes:team:orphan-check [--dry-run] [--force]` (M5c): prüft alle Teams ohne Budget und listet Team, Name, Zustand, Ergebnis, Aktion; ohne `--dry-run` werden fehlende Teams **sofort** verwaist (der Admin ist die zweite Bestätigung), gefundene verwaiste zurückgeholt; gelöscht wird nie (Frist wie oben). Gleicher Massenschutz wie der Job, aber ohne Benachrichtigung: Exit 2 mit Hinweis, `--force` übergeht ihn (z. B. Schuljahresende ohne angekommene Events). Ein Team mit Fehler steht mit Ergebnis `error` in der Liste und wird übersprungen; Circles nicht verfügbar oder alle Abfragen gescheitert → Exit 1, nichts geändert. Details §5.

Zusätzlich `UserMigration\NextNotesMigrator` (`IMigrator`, @since 24, nur Export) und `occ nextnotes:export-user`, `nextnotes:delete-user-data` (gleiche Regeln wie Kontolöschung, Abgaben bleiben), `nextnotes:assignment:transfer <assignment-id|--all-unowned> <uid> [--force]` (§9.7, ADR 0008).

Hintergrundbilder (M4g): Workspace-Löschung entfernt `backgrounds/<workspaceId>` aller Benutzer samt Deckkraft-Einstellungen; Entzug einer Freigabe entfernt die Bilder des Empfängers in diesem Workspace; Kontolöschung entfernt die Bilder in eigenen (mit dem Workspace), in freigegebenen und in den Team-Workspaces (`kind=normal`) der Teams, in denen das Konto vor der Löschung Mitglied war (`BeforeUserDeletedEvent`, Circles entfernt die Mitgliedschaft erst im `UserDeletedEvent`), sowie in Team-Workspaces mit `created_by` = uid (M5b, R15); Deckkraft-Werte dabei nicht einzeln, der Kern löscht alle Benutzerwerte. Restlücke: Bilder aus einem Team, dessen Austritts-Event verpasst wurde (Loopback), bleiben bis zur Löschung des Workspace; Team-Austritt entfernt die Bilder der uid in den Team-Workspaces dieses Teams, Umwandeln in privat alle Bilder des Workspace. Gelöscht wird nach dem Commit (`FileCleanupQueue`).

Keine automatische Löschung von Abgaben außer über die Team-Orphan-Frist (`nextnotes_teams`); kein Löschweg durch Austritt, Schülerkonto- oder Lehrkraftkonto-Löschung. Die Aufbewahrungsfrist legt die Schule fest (Datenschutzhinweis ADR 0008).

## 9. Austeilen und Einsammeln (M6)

### 9.1 Ablauf
1. Lehrkraft (Level ≥ 4) wählt eine Notiz aus einem eigenen Workspace oder einem Workspace desselben Teams (inkl. Material; verknüpfte Notiz: Ziel zählt; sonst 403 `source_not_allowed`, Lead 2026-11-08; die Oberfläche bietet seit M6i nur Notizen aus Workspaces des Teams an, „Als Aufgabe austeilen…“ nur im Team-Workspace als Lehrkraft, Team fest = Team des Workspace; die API nimmt eigene Notizen weiter an), Team, Titel, Frist (`due_at` > now) → `POST /api/v1/assignments`: Aufgabe `draft`, eingefrorene Kopie als `role=template` (inkl. Anhänge, physisch kopiert).
2. `POST /api/v1/assignments/{id}/distribute`: Status `distributed`, für jedes Team-Mitglied mit Level = 1: Abgabe (mit `student_name` = aktueller Anzeigename) + eigene Kopie (Inhalt + Anhänge) in seinem Workspace `kind=assignments` (je Schüler und Team, bei Bedarf angelegt), Ordner je Aufgabe. Pro Schüler eine Transaktion.
3. Schüler bearbeitet die Kopie (normaler Editor), `POST /api/v1/submissions/{id}/submit` → `submitted`, danach schreibgeschützt.
4. Frist: offene Abgaben werden `missed` (§9.3), Schreibzugriff wird serverseitig bei jedem Speichern geprüft.
5. Knopf in der Detailansicht (M6i-fix, Lead): Entwurf „Austeilen“; ausgeteilt nur, solange Schüler ohne Kopie fehlen (`not_distributed` > 0 aus `GET …/submissions`, z. B. Zeitbudget oder Quote), dann „An fehlende austeilen ({n})“; sonst kein Knopf (Nachzügler erhalten ihre Kopie über `reconcile`, §9.4).
6. Lehrkraft sieht alle Abgaben mit Status, schreibt Feedback (Freitext, optional Punkte ≤ `max_points`), `return` oder `reopen` (optional neue individuelle Frist).
7. Schüler sieht Feedback in seiner Abgabe (Feedback, Punkte, Name der Lehrkraft erst ab Status `returned`, auch in Listen; Thomas 2026-11-08). Lehrkraft: `GET /api/v1/assignments/{id}/export` → ZIP über `ExportArchive` (M4d-Weg: Temp-Ordner, Grenze 1 GiB, ein Export je Benutzer; `AssignmentExportService`, M6g): je Schüler Ordner `<student_name>_<uid bzw. student_uid_former>/` (Pfadzeichen ersetzt, gleicher Name → `_<Abgabe-ID>`, nie Überschreibung) mit Notiz (HTML gestaltet bzw. Markdown roh), Anhängen unter `attachments/`, `feedback.txt` (Punkte, Lehrkraft, Feedback; Beschriftung in der Sprache des Herunterladenden, M6g2); dazu `status.csv` (uid, name, status, submitted_at ISO 8601, points; Zellen, die mit `= + - @`, Tab oder CR beginnen, mit `'` präfigiert). Abgaben gelöschter Konten sind enthalten. Schüler: `GET /api/v1/submissions/{id}/export` (eigene Abgabe, `feedback.txt` erst ab `returned`).

### 9.2 Zustandsautomat `submissions.status`
| von → nach | Auslöser | Bedingung |
|---|---|---|
| (neu) → `assigned` | Austeilen/Nachzügler | Aufgabe `distributed`, now ≤ `due_at`, effektives Level = 1, keine Abgabe vorhanden |
| `assigned` → `submitted` | Schüler `submit` | now ≤ effektive Frist |
| `assigned` → `missed` | Materialisierung (§9.3) | now > effektive Frist |
| `submitted` → `returned` | Lehrkraft `return` | Feedback gesetzt (darf leer sein) |
| `submitted` → `reopened` | Lehrkraft `reopen` | optional `due_override_at` > now |
| `missed` → `reopened` | Lehrkraft `reopen` | dto. |
| `missed` → `returned` | Lehrkraft `return` | Feedback zu nicht abgegebener Arbeit |
| `returned` → `reopened` | Lehrkraft `reopen` | dto. |
| `reopened` → `submitted` | Schüler `submit` | now ≤ effektive Frist |
| `submitted` → `assigned` bzw. `reopened` | Schüler `unsubmit` („Abgabe zurückziehen“, M6g2) | eigene Abgabe, noch ohne Feedback und Punkte (`feedback_at`, `feedback`, `points` NULL), Aufgabe `distributed`, Team `active`, Level = 1, now ≤ (`due_override_at` ?? `due_at`); Prüfung unter der Notiz-Sperre; sonst 403 `submission_locked`, Aufgabe `closed` → 409 `invalid_transition`. Ziel `reopened`, wenn `due_override_at` gesetzt (eigene Frist bleibt), sonst `assigned`: Eine Abgabe aus `reopened` ohne eigene Frist fällt damit auf `assigned` zurück und es gilt wieder `due_at` (ist `due_at` vorbei, ist Zurückziehen nicht möglich). `submitted_at` = NULL. Wer nicht vor der Frist erneut abgibt, wird `missed` (Hinweis im Bestätigungsdialog) |
| `reopened` → `missed` | Materialisierung | now > effektive Frist |
| `missed` → `assigned` | Lehrkraft verlängert `due_at` (PATCH) | nur Abgaben mit `submitted_at IS NULL` und ohne `due_override_at`; neue Frist > now |
Alle anderen Übergänge → 409 `invalid_transition`. `distribute` nach Ablauf von `due_at` → 409 `deadline_passed`. Nach einer Fristverlängerung erhalten fehlende Schüler ihre Kopie beim nächsten Zugriff oder Joblauf (`reconcile`, idempotent). Der Übergang nach `missed` ist ein **berechneter** Status (§9.3), keine manuelle Aktion; er gilt auch bei verwaisten/eingefrorenen Teams. Effektive Frist = `due_override_at` falls Status `reopened` und gesetzt, bei `reopened` ohne Override keine Frist; sonst `assignments.due_at`. Feedback ändern ohne Statuswechsel (`PUT …/feedback`) in `submitted`, `missed`, `returned`. Aufgabe `closed` (Lehrkraft) sperrt die Schüler (kein Bearbeiten, kein `submit`) und `reopen` (409 `invalid_transition`); Feedback/Punkte (`PUT …/feedback`) und `return` der Lehrkraft bleiben nach den Übergängen oben erlaubt (Thomas 2026-11-08); `close` nur aus `distributed` (sonst 409 `invalid_state`), offene Abgaben (`assigned`, `reopened`) werden dabei `missed`, abgegebene bleiben `submitted`, Inhalte bleiben für die Lehrkraft lesbar. Jeder Übergang ist ein bedingtes `UPDATE … WHERE id = ? AND status = <alt>` (Wettlaufsicher); 0 Zeilen → 409.

### 9.3 Frist ohne Cron-Abhängigkeit
- `SubmissionStateService::materialize(submission, now)` setzt `assigned`/`reopened` mit abgelaufener effektiver Frist auf `missed`. Aufgerufen vor **jedem** Lesen oder Schreiben einer Abgabe oder ihrer Notiz (in `AccessService::requireNote` für `role=submission`, in allen Abgabe-Endpunkten, Listen materialisieren alle betroffenen Zeilen per bedingtem Massen-UPDATE).
- `studentCanEdit` = uid = `student_uid` ∧ Status ∈ {`assigned`, `reopened`} ∧ now ≤ effektive Frist ∧ Aufgabe `distributed` ∧ `TeamStateService::stateOf(team_id)` = `active` ∧ effektives Level des Schülers = 1 (ausgetretene Schüler: nur Lesen). Dieselbe Bedingung gilt für `submit`. Gilt für alle schreibenden Notiz-Pfade: PATCH/Beacon, Tags, Icon/Farbe/Pins/Breite/Titelstil, Konvertieren, Tasks, Anhänge (Upload/Löschen/Verschieben), Excalidraw-Speichern, Snapshot-Restore, Duplizieren. Verstoß → 403 `submission_locked`. Verschieben, Löschen und Papierkorb einer Abgabe-Notiz sind auch bei `studentCanEdit` verboten (403); die Notiz verschwindet nur mit der Aufgabe (§8).
- **Neuprüfung unter Sperre** (M6e1): Jeder Schreibweg einer Vorlage oder Abgabe sperrt die Notizzeile in seiner Transaktion und prüft das Schreibrecht dort neu (`AccessService::lockForWrite`/`recheckLocked`; PATCH, Beacon, Snapshot-Restore, Tags, Icon/Farbe/Pin/Breite/Titelstil/Favorit/Kanban, Tasks, Excalidraw, Konvertieren, Anhang hochladen/löschen). `submit/return/reopen/feedback` sperren dieselbe Zeile vor dem bedingten UPDATE der Abgabe → kein Schreiben nach `submitted`. `draft → distributed` sperrt Team → Aufgabe → Vorlagenzeile. Normale Notizen bleiben ohne Zusatzsperre.
- Zeit nur aus `ITimeFactory` (Server). `AssignmentDeadlineJob` ist nur für Benachrichtigungen und Aufräumen nötig.

### 9.6 Ansicht „Meine Aufgaben“
`GET /api/v1/assignments` ist unabhängig von Workspaces und filtert in SQL über `AccessService::visibleAssignmentIds(uid)` = Vereinigung aus (a) Aufgaben in Teams mit Zustand `active`, in denen uid aktuell Level ≥ 4 hat (Team-IDs aus `TeamService::memberTeams`, Level je Team geprüft); (b) Aufgaben mit `owner_uid = uid` in Teams mit Zustand `orphaned` oder eingefroren; (c) Aufgaben mit einer Abgabe `student_uid = uid` (Schüler, nur die eigene Abgabe). **Seite folgt dem Workspace (M6i, Thomas 2026-11-08):** `assignments.php` zeigt im Team-Workspace (`owner_type=team`, `kind=normal`) nur die Aufgaben dieses Teams (Lehrkraft-Liste und „Meine Aufgaben“, Filter im Client auf die API-Liste, keine zusätzlichen Daten); mehrere Workspaces desselben Teams zeigen dieselben Aufgaben. Kopf mit dem normalen Workspace-Chip (kein Team-Filter), „Neue Aufgabe“ nur als Lehrkraft dieses aktiven Teams, ohne Team-Auswahl. In privaten, geteilten und Schüler-Workspaces steht nur der Hinweis „Aufgaben gibt es in Team-Workspaces.“; darunter erscheinen ausschließlich Aufgaben aus Teams, für die uid keinen lesbaren Team-Workspace hat (ausgetretene Schüler, `owner_uid` verwaister/eingefrorener Teams, Team ohne `kind=normal`-Workspace, O6), damit eigene Abgaben und der Export in der Frist erreichbar bleiben (Vorschlag M6i). Der Icon-Leisten-Eintrag „Aufgaben“ erscheint nur in Team-Workspaces (`AssignmentsViewService::railLabel`, ohne Abfrage); die Hauptansicht rendert ihn immer und setzt `hidden` außerhalb von Team-Workspaces, weil der Workspace-Wechsel ohne Neuladen nur `#left_col` neu holt: der Marker `.nn-ws-scope` in `partials/left_col.php` (`data-nn-assignments`, `data-nn-teacher`) kommt mit, `nextnotes-teams.js` (MutationObserver auf `#left_col`) schaltet den Eintrag und `body[data-nn-teacher]` („Als Aufgabe austeilen…“) um; den Link pflegt Upstream `updateIconSidebarWorkspace` (M6i-fix, keine zusätzliche Anfrage, kein `src/`-Patch). „Neue Aufgabe“ ist bis zur Verdrahtung durch `nextnotes-assignments.js` ausgeblendet (`hidden`), damit ein veraltetes Skript aus dem Browser-Cache keinen toten Knopf zeigt (M6i-fix). **Links** (Banner, `assignment_deadline_passed`, `assignment_transferred`, `team_orphaned`/`team_deletion_soon` ohne eigenen Team-Workspace) tragen `workspace` = `WorkspaceService::assignmentsKey`: erster lesbarer Team-Workspace des Teams (kleinste ID, wie `WorkspaceResourceProvider`), sonst der erste eigene Workspace. Schüler-Meldungen (`assigned`, `returned`, `reopened`) verlinken weiter die eigene Kopie; deren Banner führt zur Aufgabe im Team-Workspace. Aufgaben verwaister Teams sind markiert und zeigen die Restfrist aus `nextnotes_teams.orphaned_at`, den Team-Namen aus `team_name_snapshot`. Abgaben öffnen sich dort im Lesemodus über `requireSubmission`/`requireNote`, auch wenn die Kopie-Notiz keinen Workspace mehr hat. Schüler sehen dort ihre eigenen Abgaben, auch nach Austritt. Schüler-Ansicht (M6g2): Liste eigener Aufgaben mit Status (Zugewiesen/Abgegeben/Zurückgegeben/Verpasst/Wieder geöffnet), effektiver Frist und Punkten ab `returned`; Detail mit „Bearbeiten“/„Ansehen“ (Kopie über `index.php?note=`), „Abgeben“, „Abgabe zurückziehen“, Feedback mit „Zurückgegeben von <Name>“ (Q5) erst ab `returned`, Download der eigenen Abgabe; verwaiste Teams mit Löschdatum und Export-Hinweis (Lehrkraft und Schüler).

### 9.7 Aufgaben-Rechte und Übergang (`AccessService`, `AssignmentService`)
`requireAssignment(uid, assignmentId, action)`; Team-Zustand aus `TeamStateService` (§3). „L“ = aktuelle Lehrkraft (effektives Level ≥ 4), „O“ = `owner_uid`, „S“ = Schüler mit eigener Abgabe (nur `read` auf Aufgabe und eigene Abgabe). Alles andere: ohne Leserecht 404, sonst 403.
| Aktion | aktiv | eingefroren | verwaist |
|---|---|---|---|
| read | L, S | O, S | O, S |
| review (intern: Vorlage, fremde Abgaben, Abgabenliste, Zähler; M6d) | L | O | O |
| feedback, return, reopen (auch edit, distribute, close) | L | – | – |
| export (ZIP) | L | O | O |
| delete (Aufgabe inkl. aller Abgaben, `confirm`) | L | – | O |
`owner_uid` zählt nur bei eingefrorenem oder verwaistem Team; im aktiven Team gelten allein die aktuellen Rollen.

**Übergang an Co-Lehrkraft** – benannter Systempfad `AssignmentOwnership::transferOwnership(assignmentId, reason)` (M6f, eigene Klasse statt `AssignmentService`, damit Kontolöschung und `CleanupJob` ohne die Aufgaben-Endpunkt-Abhängigkeiten auskommen) ohne Sitzung (kein `IUserSession`, keine `AccessService`-Prüfung des Aufrufers). Ziel = aktuelle Lehrkraft des Teams (höchstes Level, dann kleinste UID). `owner_uid` wird nur geändert, wenn im selben Lauf **alle drei** Bedingungen erfüllt sind: (1) `TeamService::exists()` bestätigt das Team fehlerfrei als vorhanden, (2) Circles antwortet fehlerfrei (Level-Abfragen ohne Fehler), (3) es gibt eine Ziel-Lehrkraft mit Level ≥ 4 (Kandidaten aus `TeamService::teachers`, Fehler werfen; Level des gewählten Ziels einzeln über `TeamService::currentLevel` bestätigt). Zusätzlich (M6f): Bei Austritt/Herabstufung kein Übergang, solange das Team nicht `active` ist. Sonst bleibt `owner_uid` **unverändert** – bei Austritt, Herabstufung, verpasstem Lösch-Event und unabhängig von der Reihenfolge der Events beim Auflösen eines Teams (Austritts-Events vor `CircleDestroyedEvent`); im aktiven Team gibt `owner_uid` ohnehin keine Rechte, im verwaisten bleibt so der Export in der Frist möglich. **Einzige Ausnahme Kontolöschung** (`UserDeletedEvent`): Ist kein Ziel bestätigt, wird `owner_uid` = NULL (gesperrt), weil die gelöschte UID nicht stehen bleiben darf (§2 UID-Regel); NULL entsteht auf keinem anderen Weg. Benachrichtigung `assignment_transferred`. Auslöser: Kontolöschung des `owner_uid` (§8), Austritt oder Herabstufung des `owner_uid` (Events + tägliche Prüfung im `CleanupJob`). Bedingtes `UPDATE … WHERE owner_uid = <alt>`.

**`occ nextnotes:assignment:transfer <assignment-id|--all-unowned> <uid> [--force]`**: Ziel muss existierender NC-Benutzer sein. Team `active`: Ziel muss dort aktuell Lehrkraft (Level ≥ 4) sein, sonst Fehler (auch mit `--force`). Team verwaist, eingefroren oder unbekannt (Zeile `active`, aber `exists()` meldet fehlt oder Fehler): beliebiger existierender Benutzer, nur mit `--force`. Mit `--all-unowned` ist das einzige Argument die UID; Exit 1, sobald eine Aufgabe nicht übertragen wurde (M6f). Zustand `unknown` (Circles-Fehler) mit `--force`: Ausgabe weist darauf hin, dass der tägliche Cleanup-Job (`checkDemoted`) den Besitzer still an eine Lehrkraft zurückgibt, sobald Circles das Team wieder als aktiv meldet (M6f-r1 Hinweis 3). Jeder Übertrag wird über `Psr\Log\LoggerInterface` (NC-Logger; `OCP\ILogger` ist veraltet) mit Aufgabe, altem/neuem Besitzer und Team-Zustand protokolliert.
